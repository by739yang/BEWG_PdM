## 第 1 章 作品简介

**一句话**：澜脉是一套**纯软件的污水厂设备 AI 预测性维护系统** —— 不新增任何传感器，只用厂里本来就在记录的电流、温度、压力、流量等信号，回答四个问题：**有没有异常 → 是什么故障 → 还剩多久 → 什么时候修最省**。

**解决什么痛点**：污水厂的关键设备（鼓风机、脱水机、提升泵、回流泵）目前普遍是「坏了才修 + 定期大修」：非计划停机代价高，备件与人工被浪费在还没坏的设备上；而厂里其实**已经有足够多的运行数据**，缺的是「能从数据里看出设备在退化」的方法与工具。

**项目定位**：面向市政污水厂（TO B / TO G）的**设备健康管理软件 + 接入标定服务**；形态是可离线部署的本地工具（命令行 + 本地网页工作台 + 企业版报告），不涉及硬件、不涉及垫资。

**与命题的对应**：命题 2-6 要求「基于 AI 的设备预测性维护与管理技术与解决方案」。本作品交付的是**检测 → 诊断 → 剩余寿命 → 维护决策的完整闭环**，以及**让现场把数据接进来的标定工具与报告**，而不是单点算法演示。

**作品形态一览**：见【图 A】系统架构、【图 B】四段链路、【图 C】检测判据机制。

## 第 2 章 项目创新内容

### 2.1 项目总体思路

四段链路，每段都有明确的输入、输出与验证方式（【图 B】）：

| 环节 | 回答的问题 | 方法 | 输出 |
|---|---|---|---|
| ① 检测 | 设备有没有异常/退化 | **双基线并行**（冻结抓慢漂移 + 短窗自适应抓突变）+ **工况条件化** + 事件机 | 分级告警 **P1 / P2 / P3** + 严重度（分布位置比值） |
| ② 诊断 | 是什么故障 | 振动/电流特征 + 分类器（迁移自 CWRU 轴承基准） | 部件级故障类型 |
| ③ 剩余寿命 | 还能撑多久 | **机理量**线性外推 + **趋势门控** + 拟合窗长匹配 | 剩余天数 + 可用性判定 |
| ④ 决策 | 什么时候修最省 | RUL 驱动排程 vs 固定周期/报警即处置；三项成本 + 蒙特卡洛 | 维护策略对比与节省比例 |

**七条设计原则**（全部由本项目实验独立得出，写进了代码注释与文档，是这套系统与「拿个 AI 模型套数据」的根本区别）：

| # | 原则 | 依据（本项目的实测） |
|---|---|---|
| ① | 双基线并行：短窗自适应管突变，冻结基线管慢漂移 | 慢漂移场景下自适应通道**完全漏检**（两条独立物理链路都复现） |
| ② | RUL 与严重度必须挂**机理指标** | 通用健康指数外推在长窗上误差 20.55 天，机理法 4.04 天 |
| ③ | 冻结参考域必须取自「验收合格且已进入稳态」的历史段 | 用投运暂态做参考：健康误报 26 / 18 / 26 次；稳态段 0 次 |
| ④ | 慢漂移的严重度用**分布位置统计量**（滚动中位/分位偏移） | 单点越限时刻不含严重度信息（首报时刻与退化幅值无关） |
| ⑤ | 阈值按**工况自身健康基线**标定 | 换一段进水，绝对阈值立刻失效；进一步需工况分箱与同期对拍 |
| ⑥ | RUL 拟合窗必须匹配**退化时标**并带「趋势仍在下降」门控 | 同一告警点 5/2/1 天窗 = 269.25 / 63.30 / 46.67 天（真值 47.67） |
| ⑦ | 设备级退化用**设备自身物料平衡比值**监测 | 整厂原始量 86.11 天仍检不出；比值通道 9.80 天检出 |

### 2.2 可行性分析

#### 2.2.1 技术原理科学性

**检测（【图 C】）**：对每个测点做**稳健标准化**（中位 + 鲁棒尺度：IQR/1.349 与标准差取大者，并设尺度下限），取**前 k 个最大偏离的聚合**作为异常分数，再用**事件机**（连续 4 点进入、连续 8 点低于 0.8×阈退出、冷却 8 点）把分数变成「事件」，最后按「报警 ∧ 分布位置比值」分级为 P1/P2/P3。

- **为什么必须双基线**：慢漂移会被短窗自适应基线当成「新常态」而漏检（本项目在 BSM1 与污泥线两条独立物理链路上都实测到自适应通道 **0 告警**）；反过来，固定基线在工况变化时会误报。两者互补，缺一条就会出问题。
- **为什么必须工况条件化**：把进水流量按分位分箱、箱内各自标定后，健康轨迹最高分从 **19.18 降到 14.86**，说明一部分「工况事件」能被解释掉；但要彻底消除，需要**同期同工况对拍差分**（【图 26】）。
- **为什么原始量不够**（本项目的重要负结果）：在官方 BSM2 整厂上注入脱水机退化，用 5 个原始可测量做监测，零误报口径要 **86.11 天**才报警 —— **已晚于失效 37 天**。原因是进水工况事件（+23.9%）先一步把阈值顶上去（【图 24】）。
- **RUL 的科学性**：不把「健康指数」硬外推，而是对被监测设备的**机理量**（泥饼含固率、反应池溶解氧等）做**带门控**的线性外推；机理量未出现下降趋势时**不给日期**。
- **决策的科学性**：把维护问题写成可计算的三项成本（非计划失效 / 计划更换 / 剩余寿命浪费），按退化不确定性与维护窗口做蒙特卡洛，而不是给一个「感觉更省钱」的说法。

#### 2.2.2 实施可行性：从数据到系统的落地路径

1. **数据门槛低**：只需厂里已有的运行数据导出 CSV（1 分钟或 15 分钟采样均可），无需加装传感器、无需改造 DCS；
2. **部署门槛低**：纯 Python + numpy/pandas，**零外部依赖**（无深度学习框架、无数据库、无云服务），可在一台离线工控机或办公电脑上运行；默认只在本机监听，**数据不出厂**（【图 D】）；
3. **接入有工具**：把最难的三步固定成命令 —— **体检 inspect → 标定 calibrate → 分级告警 watch**，并额外提供**企业版报告 report** 与**本地网页工作台 serve**（【图 32】）；
4. **已经在跑**：工具已在 3 个数据集上实测（真实水泵台架 SKAB、真实地铁空压机 MetroPT-3、IWA 标准模型 BSM1），并在两套机理模型中完成闭环；
5. **可复现**：一键复现（快速 9 阶段约 20 秒 / 全量 39 阶段），所有结论都对应可追溯的结果文件；
6. **可交付**：企业版报告自带「数据体检 / 标定摘要 / P1·P2·P3 告警明细 / 四张图 / 口径与局限 / 复现命令」，现场可以「拿一份数据、当场出一份报告」。

### 2.3 本项目的特色与创新之处

**创新点 1：双基线 + 工况条件化 + 对拍差分的「三层防误报」检测框架。**
同一份真实数据上，与对照实现在同等召回下误报事件**少 2.8 倍**；在整厂尺度上进一步证明单靠原始量**根本不够**，必须叠加**工况条件化**与**同期同工况对拍差分**（【图 11】【图 15】【图 16】【图 26】）。这不是调参，而是机制层面的设计。

**创新点 2：把「设备级物料平衡比值」作为退化监测量，并给出反例证据。**
在官方 BSM2 整厂（含 ADM1 消化罐、二沉池 120 态）注入脱水机退化：真值失效 **109.00 天**。5 个原始量在零误报口径下要 **86.11 天**（已晚于失效）；换成「**干固体产率 ÷ 湿泥饼量**」= 泥饼含固率代理，在 2% 仪表 + 3% 日粒度实验室噪声下 **9.80 天**检出（区间 5.03–11.03）、提前 **37.47 天**；湿泥饼量增幅 **+55.53%**（理论 28/18−1 = +55.56%）。同时该退化在全厂沼气、能耗、出水水质上几乎无痕（±0.03%）—— 说明**这类故障只能靠设备级量发现**（【图 24】【图 25】）。

**创新点 3：机理锚定的剩余寿命，并量化了「拟合窗」的坑。**
同一告警点，5/2/1 天窗给 269.25 / 63.30 / **46.67** 天（真值 47.67 天）—— 1 天窗误差 1.00 天，5 天窗误差 221.58 天；含噪后规律反转（1 天 26.47 天 → 10 天 13.85 天）。我们把这条写成规则：**窗长要同时匹配退化时标与噪声水平，且必须带趋势门控**（【图 21】）。

**创新点 4：把「诚实性」做成工程能力（可核查，而非口号）。**
- **跨实现复核**：四轮由第二套独立实现（不同作者、不共享代码）复核我们的结论，被指出的问题全部回写 —— 包括我们自己的两个口径 bug（滚动窗误用点数、平滑误用采样点数）；
- **冻结前数字总检**：脚本把每个对外数字回溯到结果文件并在文档中检索一致性，**30/30 通过**；
- **口径与限定词**：每份材料都写明「本模型 / 本轨迹 / 本噪声结构 / 本阈值口径」，并列出不可外推项（附录 C）。

### 3.2 核心模块设计

**① 检测模块**
- 输入：测点序列（可含状态列）；输出：分级告警事件流（起点、结束、持续分钟、来源通道、峰值分数、判据阈值、分布位置比值、等级）；
- 关键参数：冻结参考窗（稳态段）、工况分层（状态列 / 时段 / 负荷分位）、事件机（4 / 8 / 0.8 / 8）、分位阈值（默认 0.999）；
- 验证：真实空压机 214 天 **105 个告警**；BSM1 上工具与研究链路首报**完全一致**（40.28 天）；
- 已知边界：慢漂移下自适应通道漏检；工况变化下固定参考域误报（【图 10】【图 14】）。

**② 诊断模块**：CWRU 轴承基准上，同记录/跨转速 宏F1 **1.000**，跨故障尺寸 **0.536**（边界已标注）；下一步是与水务设备语义（轴承/叶轮/密封/气蚀）的映射。

**③ 剩余寿命模块**：C-MAPSS 涡扇基准 GBR RMSE **15.27**（PHM08 **434**，第二套实现偏差 2.4%）；孪生场景机理 RUL 误差 1.00–4.04 天；输出附「趋势是否仍在下降」门控与窗长选择规则。

**④ 决策模块**：维护策略对比（固定周期 / 报警即处置 / RUL 驱动 / 纯失效驱动），C-MAPSS 上省约 **16%**（15 格胜 12 格），污泥线脱水机省 **24.5%**（9/9 格胜）、非计划失效 0（【图 23】）。

**⑤ 接入标定工具（lanmai CLI）**：六个子命令（inspect / calibrate / watch / report / serve / selftest）；支持**多段健康期标定**（同一批数据用不同健康段标定，阈值可差 **2–4 倍**，因此必须多段，【图 11】）；参考窗有趋势时主动告警。

**⑥ 企业版报告与本地工作台**：报告把「体检 / 标定 / P1·P2·P3 / 四图 / 口径与局限 / 复现命令」渲染成**自包含单文件 HTML**（【图 31】）；工作台让现场同事**在浏览器里上传 CSV 就能出报告**（【图 32】）。

### 3.3 技术路线

数据获取（现场导出 / 公开数据）→ 数据体检与清洗 → **健康期标定**（多段 + 工况分层）→ **在线检测**（双基线 + 事件机 + 分级）→ 诊断（部件级）→ **机理 RUL**（门控 + 窗长）→ **维护决策**（成本模型）→ 回测（与检修台账比对）→ 迭代。

### 3.6 实现形态与使用说明（现场怎么用）

**A. 三种上手方式（Windows / PowerShell 实测）**

1. 双击仓库根目录的 **start_lanmai.cmd**（自动起本地工作台并打开浏览器）；
2. 命令行：进入项目目录后运行 **python run_lanmai.py serve --open**（无需配置任何环境变量）；
3. （可选）安装成工具：**python -m pip install -e . --no-build-isolation**，之后任何目录都能用 **python -m lanmai ...** 或 **lanmai ...**。

**B. 命令参考**

| 命令 | 做什么 | 常用参数 |
|---|---|---|
| lanmai inspect | 数据体检：行数、采样间隔、缺失率、零方差通道、通道统计 | --data --time --resample --channels --out |
| lanmai calibrate | 健康期标定：冻结基线 + 工况分层 + 阈值（支持多段） | --state {none,hour,col,quantile} --state-col --ref --ref-segments --thr-policy {median,upper} --q |
| lanmai watch | 输出分级告警流 | --baseline --out --warmup |
| lanmai report | 生成企业版报告（单文件 HTML） | --baseline --out --warmup --resample --max-alarms --no-fig |
| lanmai serve | 本地工作台（浏览器上传 CSV） | --host --port --out-dir --demo-dir --open |
| lanmai selftest | 冒烟自检（合成阶跃 + 慢漂移 + 回归检查） | — |

具体调用示例（四步）：

    python -m lanmai inspect   --data 现场导出.csv
    python -m lanmai calibrate --data 健康期.csv --out baseline.json --state hour --ref 0,0.3
    python -m lanmai watch     --data 待监测.csv --baseline baseline.json --out alarms.csv --warmup 1D
    python -m lanmai report    --data 待监测.csv --baseline baseline.json --out report.html --warmup 1D

**C. 本地工作台六步操作**（【图 32】）

1. 启动工作台并打开浏览器；2. 上传「健康期数据」→ 选工况分层与参考段 → 生成 baseline.json；3. 上传「待监测数据」+ baseline.json → 生成 report.html；4. 浏览器直接打开报告；5. 在「产物列表」里下载明细；6.（可选）点「样例一键试跑」验证环境。

**E. 现场接入的 POC 四步**（【图 35】）

1. 选 **1 台**设备（建议鼓风机 / 脱水机 / 泵），取 **≥12 个月**历史数据 + 检修台账；
2. 用**不含故障的历史段**标定基线（工具会告警参考段是否有趋势，需现场确认该段确无检修/故障）；
3. 用**含故障的历史段**回放验证：对比「首报时间」与「台账真实故障时间」，算**提前量**与**误报数**；
4. 通过后进入在线运行：P1 立即处置 / P2 复核排计划 / P3 趋势观察；每月出报告，季度复盘并逐步扩设备。

## 第 4 章 价值、潜力及影响

**技术价值**：把「预测性维护」从概念变成**可离线部署、可现场标定、可核查数字**的工程工具；七条设计原则与四轮跨实现复核，为同类项目提供了可复用的方法学。

**社会价值**：① 减少非计划停机与溢流风险，提高污水处理稳定性；② 污泥处置合规（泥饼含固率不达标场景有明确提前预警）；③ 与「双碳」方向一致 —— 按状态维护可减少备件与能耗浪费；④ **不需要新增传感器**，不增加现场改造负担与电子垃圾。

**经济价值（潜力）**：面向污水厂的**软件订阅 + 接入标定服务**；单厂按关键设备数计价，轻资产、不垫资。市场规模、定价与竞争分析详见《商业计划书》（deliverables/ppt/澜脉_商业计划书.pptx）。**当前所有成本与收益数字均为占位值。**

**推广路径**：① 单厂单设备试点（3–6 个月）→ ② 单厂多设备（鼓风机 / 脱水机 / 泵）→ ③ 集团多厂复制（阈值与工况分层可按厂标定）→ ④ 横向扩展到供水厂与排水管网泵站（同一套「双基线 + 工况条件化 + 机理 RUL」框架）。

**影响与局限（主动声明）**：污水厂侧结论均来自机理仿真；真实设备目前只有水泵台架与地铁空压机；浓缩/脱水为理想单元（无堵塞、无动力学）；成本参数为占位值；诊断跨故障尺寸精度有限；未覆盖相关漂移与多传感器联合漂移；判据存在刀锋边缘情形。

## 附录 A 常见问题（FAQ）

**Q1 我们没有现成的运行数据导出，怎么办？**
先确认 DCS/SCADA 能否导出历史趋势（CSV/Excel 即可）；若只能导一天，也能演示「上传 → 体检 → 标定 → 报告」这条链路，但要评估退化必须 ≥ 数月数据。

**Q2 工具提示「参考窗有显著趋势」，还能用吗？**
不能直接用。这说明你给的「健康期」可能不是稳态（可能有检修、季节升温等）。处理方式：换一段更干净的健康期，或用多段健康期标定（--ref-segments）取中位/保守策略。

**Q3 告警太多怎么办？**
三步：① 提高分位阈值 q（更保守）；② 用多段标定的 upper 策略压误报；③ 只把 P1 纳入立即处置，P2 复核、P3 观察。另外检查是否漏了工况分层（--state col）。

**Q4 会不会和现有 DCS 报警冲突？**
不冲突也不替代：我们的输出是「设备级退化趋势与剩余寿命建议」，P1/P2/P3 是维护动作分级；建议先与既有报警并跑 1–3 个月再合并流程。

**Q5 部署要什么配置？**
任意能跑 Python 3.9+ 的机器（工控机/办公电脑即可）；只要 numpy/pandas；无需 GPU、无需外网、无需数据库。

**Q6 数据安全怎么保证？**
默认只监听本机 127.0.0.1，全部计算与落盘在本机完成；报告是单文件 HTML，可只在内部流转；如需局域网访问，显式加 --host 0.0.0.0 并自行控制网络范围。

**Q7 怎么证明它真的有效？**
用历史回放：拿一段包含真实故障的数据，比较「首报时间」与「台账故障时间」的提前量，以及这段期间的误报数 —— 这就是我们建议的 POC 第 3 步。

**Q8 成本参数从哪来？**
需要企业提供三项：一次非计划失效的损失、一次计划更换的费用、以及剩余寿命被浪费的折算口径。**未标定前，我们不对外给任何金额。**

**Q9 诊断精度够用吗？**
同记录/跨转速很好（宏F1 1.000），跨故障尺寸有限（0.536），已在材料中标注；现阶段建议把诊断作为「辅助定位」，主决策依据仍是检测与 RUL。

**Q10 RUL 会不会不准？**
会，而且我们量化过：机理量未下降时不给日期；窗长不匹配时误差可达 200 天以上；含噪时 1 天窗误差 26 天、10 天窗 13.85 天。因此 RUL 建议与维护窗口一起用，并保留人工确认。

## 附录 E 术语表

| 术语 | 含义 |
|---|---|
| 双基线 | 冻结基线（固定参考域，抓慢漂移）+ 自适应基线（短窗，抓突变）并行 |
| 工况条件化 | 按运行状态/时段/负荷分箱，各箱内单独标定阈值 |
| 对拍差分 | 用同期同工况的健康轨迹与当前轨迹做配对差分，消掉共同工况波动 |
| 事件机 | 把逐点分数转成事件的规则（连续 4 点进入 / 连续 8 点低于 0.8×阈退出 / 冷却 8 点） |
| P1/P2/P3 | 报警 ∧ 分布位置抬升 = 立即处置 / 仅报警 = 复核排计划 / 仅分布位置抬升 = 趋势观察 |
| 机理量 | 与设备退化有物理因果的量（泥饼含固率、反应池溶解氧等），用于 RUL |
| 参考域 | 标定用的健康历史段，必须是验收合格且进入稳态的时段 |
| RUL | Remaining Useful Life，剩余使用寿命 |
