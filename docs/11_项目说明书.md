## 第 1 章 作品简介

**一句话**：澜脉是一套**纯软件的污水厂设备 AI 预测性维护系统** —— 不新增任何传感器，只用厂里本来就在记录的电流、温度、压力、流量等信号，回答四个问题：**有没有异常 → 是什么故障 → 还剩多久 → 什么时候修最省**。

**解决什么痛点**：污水厂的关键设备（鼓风机、脱水机、提升泵、回流泵）目前普遍是「坏了才修 + 定期大修」：非计划停机代价高、备件与人工被浪费在还没坏的设备上；而厂里其实**已经有足够多的运行数据**，缺的是「能从数据里看出设备在退化」的方法与工具。

**项目定位**：面向市政污水厂（TO B / TO G）的**设备健康管理软件与接入标定服务**；形态是可离线部署的本地工具（命令行 + 本地网页工作台 + 企业版报告），不涉及硬件与垫资。

**与命题方向的对应**：命题 2-6 要求「基于 AI 的设备预测性维护与管理技术与解决方案」；本作品给出的是**从检测、诊断、剩余寿命到维护决策的完整闭环**，以及**能让现场把数据接进来的标定工具**，而不是单点算法演示。

## 第 2 章 项目创新内容

### 2.1 项目总体思路

四段链路，每段都有明确输入输出与验证方式：

| 环节 | 回答的问题 | 方法与输出 |
|---|---|---|
| ① 检测 | 设备有没有异常/退化 | **双基线并行**（冻结基线抓慢漂移 + 短窗自适应抓突变）+ **工况条件化**阈值 + 事件机 → 分级告警 **P1 / P2 / P3** |
| ② 诊断 | 是什么故障 | 振动/电流特征 + 分类器（迁移自 CWRU 轴承基准）→ 部件级故障类型 |
| ③ 剩余寿命 | 还能撑多久 | **机理量**（如脱水机泥饼含固率、反应池溶解氧）线性外推 + **趋势门控** + 拟合窗长匹配 |
| ④ 决策 | 什么时候修最省 | RUL 驱动排程 vs 固定周期/报警即处置：算非计划失效、计划更换与剩余寿命浪费三项成本 |

**七条设计原则**（全部由本项目实验独立得出，写进代码注释与文档，是这套系统与「拿个 AI 模型套数据」的根本区别）：

1. **双基线并行**：短窗自适应管突变（对慢漂移免疫），冻结基线管慢漂移（对突变不灵敏）；两路报警合并时标注来源；
2. **RUL 与严重度必须挂机理指标**：不用通用健康指数外推代替机理量；
3. **冻结参考域必须取自「验收合格且已进入稳态」的历史段**：投运暂态段做参考会把阈值压坏（本项目实测：健康误报 26 / 18 / 26 次 vs 稳态段 0 次）；
4. **慢漂移的严重度用分布位置统计量**（滚动中位数/分位数偏移）：单点越限时刻不含严重度信息；
5. **阈值按工况自身健康基线标定**：换一段进水/负荷，绝对阈值立刻失效（本项目实测跨工况 0 误报不成立）；进一步需要**工况分箱条件化**，甚至**同期同工况对拍差分**；
6. **RUL 的机理拟合窗必须匹配退化时标，并带「趋势仍在下降」门控**；含噪时窗长还要匹配噪声水平；
7. **设备级退化要用设备自身的物料平衡比值监测**（如「干固体产率 / 湿泥饼量」= 含固率），不能只看全厂原始量。

### 2.2 可行性分析

#### 2.2.1 技术原理科学性

- **检测**：对每个测点做**稳健标准化**（中位 + 鲁棒尺度，IQR/1.349 与标准差取大者，并设尺度下限），再取**前 k 个最大偏离的聚合**作为异常分数，最后用**事件机**（连续 4 点进入、连续 8 点低于 0.8×阈退出、冷却 8 点）把分数变成「事件」。这套组合的每一步都有消融/敏感性证据支撑。
- **为什么必须双基线**：慢漂移会被短窗自适应基线当成「新常态」而漏检（本项目在两条独立物理链路上都实测到自适应通道**完全漏检**）；反过来，固定基线在工况变化时会误报 —— 两者互补，缺一条就会出问题。
- **工况条件化的必要性**：把进水流量按分位分箱、箱内各自标定后，健康轨迹的最高分从 19.18 降到 14.86，说明「工况事件」确实能被解释掉一部分；但要彻底消除，需要**同期同工况对拍差分**（我们用它把设备级退化的可检出性从「检不出」变成「失效前 14.5 天」）。
- **RUL 的科学性**：不把「健康指数」硬外推，而是对被监测设备的**机理量**（含固率、溶解氧、流量比等）做带门控的线性外推；并明确「机理量未出现下降趋势时不给日期」。
- **决策的科学性**：把维护问题写成可计算的三项成本（非计划失效 / 计划更换 / 剩余寿命浪费）并按退化不确定性与维护窗口做蒙特卡洛，而不是给一个「感觉更省钱」的说法。

#### 2.2.2 实施可行性：从数据到系统的落地路径

1. **数据门槛低**：只需要厂里已有的运行数据导出为 CSV（1 分钟或 15 分钟采样均可），无需加装传感器、无需改造 DCS；
2. **部署门槛低**：纯 Python + numpy/pandas，**零外部依赖**（无深度学习框架、无数据库、无云服务），可在一台离线工控机或办公电脑上运行；默认只在本机监听，**数据不出厂**；
3. **接入有工具**：已提供「接入标定工具」把最难的三步固定成命令 —— **体检（inspect）→ 标定（calibrate）→ 分级告警（watch）**，并额外提供**企业版报告（report）**与**本地网页工作台（serve）**；
4. **已经在跑**：工具已在 3 个真实/仿真数据集上实测（真实水泵台架 SKAB、真实地铁空压机 MetroPT-3、IWA 标准模型 BSM1），并在两套机理模型中完成「注入退化 → 检测 → RUL → 决策」闭环；
5. **可复现**：仓库提供一键复现（快速 9 阶段约 20 秒 / 全量 39 阶段），所有结论都对应可追溯的结果文件；
6. **可验证**：企业版报告自带「数据体检 / 标定摘要 / P1·P2·P3 告警明细 / 四张图 / 口径与局限 / 复现命令」，现场可以「拿一份数据、当场出一份报告」。

### 2.3 本项目的特色与创新之处

**创新点 1：双基线 + 工况条件化 + 对拍差分的「三层防误报」检测框架。**
同一份真实数据上，与对照实现相比，在同等召回下误报事件少 **2.8 倍**；而在整厂尺度上，我们进一步证明单靠原始量**根本不够**（见创新点 2），必须加工况条件化与对拍差分。这不是调参，而是机制层面的设计。

**创新点 2：把「设备级物料平衡比值」作为退化监测量 —— 并给出了反例证据。**
在官方 BSM2 整厂（含 ADM1 消化罐、二沉池 120 态）上注入脱水机退化：真值失效第 **109.00** 天。用 5 个原始可测量做监测，在零误报口径下要 **86.11 天**才报警（**已晚于失效 37 天**），原因是进水工况事件（流量 +23.9%）先一步把阈值顶上去；换成设备级比值「**干固体产率 / 湿泥饼量**」，在 2% 仪表 + 3% 日粒度实验室噪声下 **9.80 天**检出（区间 5.03–11.03）、提前 **37.47 天**，并且湿泥饼量增幅 **+55.53%**（与理论 28/18−1 = +55.56% 吻合）。

**创新点 3：机理锚定的剩余寿命，并量化了「拟合窗」的坑。**
同一告警点，5/2/1 天窗给出的 RUL 是 269.25 / 63.30 / **46.67** 天（真值 47.67 天）——1 天窗误差 1.00 天，5 天窗误差 221.58 天。含噪后规律反转：1 天窗误差 26.47 天 → 10 天窗 13.85 天。我们把这条写成规则：**窗长要同时匹配退化时标与噪声水平，并且必须带趋势门控**。

**创新点 4：把「诚实性」做成工程能力（可核查，而不是口号）。**
- **跨实现复核**：四轮由第二套独立实现（不同作者、不共享代码）复核我们的结论，被指出的问题全部回写（包括我们自己的两个口径 bug：滚动窗误用点数、平滑误用采样点数）；
- **冻结前数字总检**：脚本把每个对外数字回溯到结果文件并在文档中检索一致性，**30/30 通过**；
- **口径与限定词**：每份材料都写明「本模型 / 本轨迹 / 本噪声结构 / 本阈值口径」，并列出不可外推项（例如成本参数目前是占位值、污水厂侧结论全部来自机理仿真）。

## 第 3 章 实施方案

### 3.1 系统架构（四层）

| 层 | 内容 | 交付物 |
|---|---|---|
| 数据层 | 现场 CSV 导出（时间戳 + 模拟量 + 状态列）；体检与清洗 | 接入标定工具 inspect |
| 算法层 | 双基线检测 / 工况条件化 / 事件机 / 诊断 / 机理 RUL / 维护决策 | 研究链路脚本（可复现） |
| 服务层 | 本地网页工作台（上传 → 标定 → 报告）；命令行工具 | lanmai serve / lanmai CLI |
| 交付层 | 企业版报告（单文件 HTML）、演示页与演示台、复现包 | report.html / Pages / run_all.py |

### 3.2 核心模块设计

**① 检测模块（lanmai.core / pipeline + 研究链路 dual_baseline）**
- 输入：测点序列（可含状态列）；输出：分级告警事件流（起点、结束、持续、来源通道、峰值分数、判据阈值、分布位置比值、等级）；
- 关键参数：冻结参考窗（稳态段）、工况分层（状态列 / 时段 / 负荷分位）、事件机（4 / 8 / 0.8 / 8）、分位阈值（默认 0.999）；
- 验证：真实空压机 214 天 105 个告警；BSM1 上工具与研究链路首报**完全一致**（40.28 天）；
- 已验证的失效边界：慢漂移下自适应通道漏检；工况变化下固定参考域误报。

**② 诊断模块**：CWRU 轴承基准上，同记录/跨转速 宏F1 **1.000**，跨故障尺寸 **0.536**（边界已在材料中标注）；下一步是与水务设备语义（轴承/叶轮/密封/气蚀）的映射。

**③ 剩余寿命模块**：C-MAPSS 涡扇基准 GBR RMSE **15.27**（PHM08 **434**，第二套实现偏差 2.4%）；孪生场景机理 RUL 误差 1.00–4.04 天；输出附「趋势是否仍在下降」门控与窗长选择规则。

**④ 决策模块**：维护策略对比（固定周期 / 报警即处置 / RUL 驱动 / 纯失效驱动），在 C-MAPSS 上 AI 省约 **16%**（15 格中胜 12 格），在污泥线脱水机场景省 **24.5%**（9/9 格胜）、非计划失效 **0**；**成本参数为占位值**。

**⑤ 接入标定工具（lanmai CLI）**：inspect / calibrate / watch / report / serve / selftest 六个子命令；支持多段健康期标定（同一批数据用不同健康段标定，阈值可差 **2–4 倍**，因此必须多段）；参考窗有趋势时主动告警。

**⑥ 企业版报告与本地工作台**：报告把「体检 / 标定 / P1·P2·P3 / 四图 / 口径与局限 / 复现命令」渲染成**自包含单文件 HTML**；工作台让现场同事**在浏览器里上传 CSV 就能出报告**（数据不出本机）。

### 3.3 技术路线

数据获取（现场导出/公开数据）→ 数据体检与清洗 → **健康期标定**（含多段与工况分层）→ **在线检测**（双基线 + 事件机 + 分级）→ 诊断（部件级）→ **机理 RUL**（门控 + 窗长）→ **维护决策**（成本模型）→ 回测（与检修台账比对）→ 迭代。

### 3.4 实验与验证手段（这是「技术可行性」的正面回答）

| 数据/模型 | 类型 | 用途 | 关键结果 |
|---|---|---|---|
| SKAB | 真实水泵台架（人工注入故障） | 异常检测主实验 | 三方法**双实现零偏差**；DET 曲线定稿 |
| MetroPT-3 | 真实地铁空压机，214 天 | 真实故障验证 | 冻结口径及时命中 2/4（**标签辅助选点**）；无标签口径 0/4，如实声明 |

### 3.5 关键技术方案（难点 → 对策）

| 难点 | 对策 |
|---|---|
| 慢漂移 vs 工况漂移混在一起 | 双基线并行；**工况分箱条件化**；仍需彻底消除时用**同期同工况对拍差分** |
| 参考段选不干净 | 工具主动检测参考窗趋势并告警；要求多段健康期标定 |
| 假 RUL（把传感器漂移当设备退化） | 要求多源冗余（在线密度计 + 实验室）+ **独立漂移监控**；RUL 只挂机理量且带趋势门控 |
| 判据处在刀锋边缘 | 明确标注（例：在线门禁分布位置比 1.250487 vs 阈值 1.25），不把边缘结果当稳定性能 |
| 成本无法引用 | 提供可参数化的成本模型；**未标定前一律标注占位值** |

### 3.6 实现形态与使用说明（现场怎么用）

**A. 三种上手方式（Windows / PowerShell 实测）**
1. 双击仓库根目录的 **start_lanmai.cmd**（自动起本地工作台并打开浏览器）；
2. 命令行：进入项目目录后运行 **python run_lanmai.py serve --open**（无需配置任何环境变量）；
3. 安装成工具（可选）：**python -m pip install -e . --no-build-isolation**，之后任何目录都能用 **python -m lanmai ...** 或 **lanmai ...**。

**B. 四条核心命令**

    python -m lanmai inspect   --data 现场导出.csv
    python -m lanmai calibrate --data 健康期.csv --out baseline.json --state hour --ref 0,0.3
    python -m lanmai watch     --data 待监测.csv --baseline baseline.json --out alarms.csv --warmup 1D
    python -m lanmai report    --data 待监测.csv --baseline baseline.json --out report.html --warmup 1D

**C. 本地工作台的六步操作**（截图见随文图 5）
1. 启动工作台；2. 上传「健康期数据」→ 选工况分层与参考段 → 生成 baseline.json；3. 上传「待监测数据」+ baseline.json → 生成 report.html；4. 浏览器直接打开报告；5. 在「产物列表」里下载明细；6.（可选）点「样例一键试跑」验证环境。

**D. 现场接入的 POC 四步（我们建议的试点方式）**
1. 选 **1 台**设备（建议鼓风机 / 脱水机 / 泵），取 **≥12 个月**历史数据 + 检修台账；
2. 用**不含故障的历史段**标定基线（工具会告警参考段是否有趋势，需现场确认该段确无检修/故障）；
3. 用**含故障的历史段**做回放验证：对比「首报时间」与「台账真实故障时间」，算**提前量**与**误报数**；
4. 通过后进入在线运行：P1 立即处置 / P2 复核排计划 / P3 趋势观察；每月出一份报告，季度复盘。

## 第 4 章 价值、潜力及影响

**技术价值**：把「预测性维护」从概念变成**可离线部署、可现场标定、可核查数字**的工程工具；七条设计原则与四轮跨实现复核，为同类项目提供了可复用的方法学。

**社会价值**：① 减少非计划停机与溢流风险，提高污水处理稳定性；② 污泥处置合规（泥饼含固率不达标的场景有明确的提前预警）；③ 与「双碳」方向一致 —— 按状态维护可减少备件与能耗浪费；④ 不需要新增传感器，**不增加电子垃圾与现场改造负担**。

**经济价值（潜力）**：面向污水厂的**软件订阅 + 接入标定服务**；单厂按关键设备数计价，轻资产、不垫资。市场规模、定价与竞争分析详见《商业计划书》（PPT）。**当前所有成本与收益数字均为占位值，需用现场参数标定。**

**推广路径**：① 单厂单设备试点（3–6 个月）→ ② 单厂多设备（鼓风机/脱水机/泵）→ ③ 集团多厂复制（阈值与工况分层可按厂标定）→ ④ 横向扩展到供水厂与排水管网泵站（同一套「双基线 + 工况条件化 + 机理 RUL」框架）。

**局限（主动声明）**：污水厂侧结论均来自机理仿真（材料中一律标注仿真）；真实设备目前只有水泵台架与地铁空压机；浓缩/脱水为理想单元（无堵塞与动力学）；成本参数为占位值；诊断跨故障尺寸精度有限；未覆盖相关漂移与多传感器联合漂移。
