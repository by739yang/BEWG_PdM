# 对 DSH 技术结论的独立审查（Codex）

## 可复现命令与审查边界

```powershell
python src/codex/2026-09-15_03_review_dsh.py
```

只读输入：`results/2026-09-15/dsh/demo_results_v5.csv`、`results/2026-09-15/dsh/*.md`、`logs/实验日志.md` 与 SKAB 原始标签。没有读取 `src/dsh/` 或 `demo_*.py`。

## 先说总评

DSH 当前结果能支持“现有实现存在明显检出-误报权衡”，但还不能支持“单一模型必然偏科”或“自编码器在工业小样本+漂移场景不适用”这类模型类别级结论。融合取并集从 88.2% 提升到日志所报 91.2%，同时误报从 15.9% 增至日志所报 34.7%；这是并集规则的机械性质，不是已经证明的互补性或工程收益。必须在相同误报预算下比较 DET/事件召回，才有资格谈优越。

## 1. “误报分钟比例”会不会被 61% 故障基数误导？

### 结论

**如果定义严格为 `FP / 正常分钟数`，它本身不会被故障基数直接稀释；被 61% 基数严重误导的是 accuracy、precision、逐点/逐分钟 F1。** 但当前误报分钟比例仍不足以单独代表现场价值，因为正常分钟分母很小、块规则放大误报、文件池化掩盖设备差异，而且它没有告诉运维人员一天会收到多少次可操作报警。

### 本地标签复核

- 34 个故障文件在各自 `floor(0.4N)` 后共有 22,451 个逐秒样本，其中故障样本 12,859，故障基数 57.3%；恒报正类的逐点 F1 已有 0.728。
- 用本审查明确的“从 40% 处起每 60 行一块、块内任一点故障即故障块”定义，共 390 块、故障块 253，基数 64.9%；恒报正类的块 F1 达 0.787。块锚点不同会改变该数，因此 DSH 日志的约 61% 与本实现不必完全相同，但问题本质一致。
- DSH 报告的固定报警值 F1=0.668、PCA F1=0.436，都低于其平凡基线 F1=0.761；因此不能把 F1 当主要卖点。
- 0.5% 是逐秒标定分位时，若逐秒越限近似独立，60 秒块内“任一点即报警”的理论块误报概率为 `1-(1-0.005)^60≈26.0%`。所以 15.9%/19.7% 的分钟误报不是意外，而是判决聚合规则的直接后果；真正应该标定的是块级或报警事件级阈值。

### 建议替代/补充指标

1. **首要指标：每设备每健康运行小时的独立误报事件数**。先用迟滞、最短持续时间和冷却期把连续报警合并成 episode；分母只计健康且设备实际运行的小时。DSH 日志已承认当前“误报事件次/时”合并逻辑失效，应重做而非删除该指标。
2. **健康时间在报警状态的比例**（time-in-alarm / normal operating time），即现有误报分钟比例，但应按设备分别报告中位数、IQR、最坏值和置信区间，不能只池化。
3. **事件级召回 + 提前量/延迟分布**：报警必须落在事先定义的预警窗或故障窗内；只要文件后半段任意时刻报一次就算检出，会把无关误报当命中。
4. **DET/operation-point 曲线**：横轴独立误报事件/健康小时，纵轴事件召回，并附延迟；所有模型在相同误报预算下比较。
5. 辅助报告 AUPRC、MCC、balanced accuracy；不要把受人工故障占比支配的普通 F1 作为核心图。

## 2. “文件前 40% 标定”在真实污水厂是否成立？

### 结论

**通常不成立。** 文件边界是数据导出边界，不是设备健康状态边界；现场不会保证每个文件前 40% 无故障、同工况、无维护、无漂移。该规则还会让训练时长随文件总长度变化，未来数据文件越长，模型实际上越“偷看”更多早期历史，难以形成部署协议。

### SKAB 内部反证

- 标定段含故障的文件数：1；文件：other/2.csv。
- 具体早发事件（故障起点行 < 40% 截止行）：other/2.csv: start=104, cal_end=312。
- 这说明即使在人工实验数据上，固定比例健康假设也已经被违反；真实厂站只会更复杂。

### 我会怎么改

1. 用**维修/投运后的确认健康时间段**初始化，而不是文件百分比；明确最少健康运行小时和覆盖工况数。
2. 采用严格因果 walk-forward：模型只用当前时刻之前、且未被报警/质量门禁隔离的数据更新；疑似异常进入 quarantine，人工确认后再决定是否回灌。
3. 先分工况（停机/启动/稳态低负荷/高负荷/反冲洗等），每个工况单独维护基线或做条件模型，避免把工况切换当故障。
4. 设漂移与重标定门禁：传感器更换、检修、控制策略变化后重置；日常漂移只允许限速更新，并保留冻结基线作对照。
5. 评估用滚动起点/多时间切分：在多个历史截点重复“只看过去预测未来”，报告跨设备、跨季节的分布，而不是单次前 40%/后 60%。

## 3. 如果从零设计，我先做什么；今天哪些实验先不做

### 我会先做

1. **先定义决策问题和报警单位**：什么故障需要提前多久、漏报和一次误报各多少钱、报警如何合并、谁处理。没有这些，模型分数无法映射成维护动作。
2. **先做传感器质量 + 工况状态层**：常值/卡死/漂移/缺测门禁，泵启停与负荷分层；把“设备故障”和“传感器故障/工况变化”分开。PROJECT_STATE 已有流量恒定与热漂移两个真实陷阱，应优先产品化为质量规则。
3. **再做最简单的可解释基线**：同工况内的 robust residual/EWMA/CUSUM，加事件化报警、迟滞和冷却期；先把误报事件/健康小时压到业务可接受水平，再谈复杂模型。
4. **用两个真实数据集做时间外验证**：SKAB 验证人工故障可检测性，MetroPT-3 验证连续运营、维修边界与真实空气泄漏；不要用同一协议参数硬套不同采样和工况。

### 今天我会先不做

- **先不做 1D 卷积自编码器。** 在标定污染、工况未分层、报警事件指标未定义时，AE 的 23.5%/17.6% 只能说明当前训练/阈值实现失败，不能说明 AE 类方法不适用。继续调网络只会把数据协议问题藏进超参数。
- **先不做“变点 + PCA 取并集”作为主方案。** 并集天然提高召回和误报；在没有相同误报预算、报警合并和成本函数时，91.2% 不是有效的系统胜利。
- 也不做大规模模型排行榜。当前最缺的不是第四、第五个检测器，而是部署一致的标定协议、事件定义和误报工作量指标。

## 最终审查结论（不超过 3 条）

1. “误报控制是瓶颈”方向基本正确；但必须把核心横轴改成独立误报事件/健康运行小时，并在相同误报预算下比较模型。
2. “单一模型必然偏科”“AE 在工业小样本+漂移下不适用”均为过度外推；现有证据只覆盖一个数据集、一套特征/阈值和一个 AE 实现。
3. 在任何深度模型或融合前，先完成传感器质量门禁、工况条件化、维修后 walk-forward 标定和事件化报警；这比继续堆模型更接近真实污水厂。
